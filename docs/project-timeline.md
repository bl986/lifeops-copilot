# Project timeline: LifeOps OS, AI Portfolio Copilot

This is the story of how I built this project, in order: what I built, what broke, how I found the cause, and how I fixed it. I built it with AI assistance (vibe coding). One AI wrote the first version, a second AI reviewed it, and I made the decisions and checked every change with diffs, tests, CI and live requests.

**Live demo:** https://lifeops-copilot.onrender.com

## 1. Goal and scope

I wanted a free, public project that shows I can design, build, test and troubleshoot an AI agent, not just call a model API. My checklist was:

- Architecture and system design
- A custom MCP server
- Agent skills
- Harness engineering (guardrails, testing the agent)
- AI-written SQL against a real database
- A deployed server with throughput controls
- Python throughout
- Tests for AI-written code, and AI reviewing AI-written code

The idea started as a cloud troubleshooting assistant. I moved to a portfolio chatbot instead: visitors ask about my background, and the agent pulls answers from tools and a small database. The sample data (expenses and tasks) gives the SQL part something to query.

## 2. Stack decisions

- **Language and API:** Python, FastAPI, Uvicorn.
- **Model:** Gemini through the `google-genai` SDK, which has a free tier.
- **Database:** SQLite. It needs no server, it ships inside the repo, and it is enough for a demo.
- **MCP:** the `mcp` package (FastMCP). I pinned `mcp<2.0.0` after version 2.x broke the import.
- **Hosting:** Render free tier, auto-deployed from GitHub on every push. I first looked at Hugging Face Spaces, but custom backends need a paid plan there.
- **Tests and CI:** pytest, run by GitHub Actions on every push.

## 3. First build

I set up a virtual environment, a 3-table SQLite database (`portfolio`, `expenses`, `tasks`), and a FastMCP server with two tools: one to read my portfolio, one to turn a question into SQL with Gemini and run it. A pytest file checked the tables, the portfolio tool and the SQL tool. All 3 tests passed locally.

Small problems along the way, all fixed:
- PowerShell rejected a multi-folder `mkdir`, blocked venv activation (fixed with `Set-ExecutionPolicy RemoteSigned -Scope Process`), and ran `pytest` from the wrong Python until the venv was active.
- Gemini model names kept changing. At one point `gemini-2.5-flash` returned "no longer available to new users", so I moved to a newer model and later made the model name configurable with the `GEMINI_MODEL` environment variable.

## 4. Going live

I deployed to Render (Python 3, build `pip install -r requirements.txt && python backend/database.py`, start `uvicorn backend.main:app --host 0.0.0.0 --port $PORT`, with the API key stored as a masked environment variable).

- The first deploy crashed with `ModuleNotFoundError`. The imports needed the full `backend.` package path.
- The page then showed "index.html not found" because the file had never been written.

## 5. Frontend bug: "Send does nothing"

Send did nothing, and the console showed `sendMessage is not defined`, then `Unexpected token '<'`. It took a long time to find the cause. The assistant suggested CORS, caching and the favicon, and none of those were it. The real cause was my terminal: PowerShell here-strings were mangling backticks and quotes inside the JavaScript I had pasted in.

The fix was to split the page into `index.html`, `static/style.css` and `static/app.js`, and to fix the one remaining mangled line. After that I added a dark theme, markdown rendering, and a rule so job titles never turn into fake links.

## 6. Finding a silent regression, then rebuilding

Later, a rewrite generated by the first AI overwrote working code without any warning:
- The FastMCP server became two plain functions, so there was no MCP left.
- The model-written SQL tool became an `if/else` that always returned one hardcoded query.
- The database shrank to one table, and the 3 passing tests could no longer run.

A second AI reviewed my chat export and then my actual files. I decided what to apply. The review found these problems:
- A leftover `index.html` stub was being served (wrong element IDs, no call to `/chat`).
- `runtime.txt`, `Dockerfile` and `Procfile` were being ignored by Render, so the app ran on Python 3.14.
- An API key had been pasted into a chat, so I rotated it. It now lives only in Render's masked field.
- The public `/chat` endpoint had no rate limit and returned raw error text.
- CORS was misconfigured.
- My earlier notes claimed more than the code did.

My fixes:
- **Workflow:** I switched to editing in github.dev (a browser editor) and reading the diff before each commit, instead of pasting whole files into a terminal.
- **Python version:** I pinned it with `.python-version` (3.11.9) and added a `/health` endpoint that reports the Python version and model, so I can prove it.
- **Database layer:** I rebuilt `database.py` with two protections for model-written SQL. A validator allows a single `SELECT` only, with no comments and no write or schema keywords. The query then runs on a read-only SQLite connection (`mode=ro`), so even a bypassed validator cannot change data. Results are capped at 50 rows.
- **MCP server:** I restored a real FastMCP server with model-written SQL running through those guards.
- **Tests:** I rewrote the suite. Each test gets a throwaway database. It checks injection attempts (`DROP`, `DELETE`, `UPDATE`, stacked statements, comments, `PRAGMA`), the read-only connection, the tools and the harness. It also caught a real bug: the harness reported "success" for an empty model reply.
- **CI:** GitHub Actions runs the tests on every push.

## 7. Making it a real agent

The early version picked data with keyword `if` statements. I replaced that with Gemini function calling in `agent.py`: the model sees the tools and decides which one to call, with a maximum of 3 tool calls per question. `main.py` now only validates input, rate limits and routes.

A live bug taught me something. "How much did I spend on groceries?" returned $0. I read the SQL the model had written (the API returns it in `tools_called`): `WHERE category = 'groceries'`, but the data said `'Groceries'`, and SQLite compares text case-sensitively. Fixes: `COLLATE NOCASE` in the schema, a prompt rule, and a regression test. The answer became $148.70.

## 8. Hardening

- **Rate limits:** a sliding window of 10 requests a minute per IP and 300 an hour overall, returning `429` with a `Retry-After` header. The global cap protects my free quota, because per-IP headers can be spoofed.
- **Input:** messages are limited to 500 characters.
- **Errors:** details are logged on the server and visitors see a generic message.
- **Output:** all model text is HTML-escaped before it reaches the page, quotes are escaped so a crafted link cannot break out of an attribute, links get `rel="noopener noreferrer"`, and only `https://` links are rendered.
- **Dependencies:** test packages moved to `requirements-dev.txt`, so production installs stay small.
- **Public text:** I corrected my employment description, pronouns and dates in the portfolio data, and removed personal details I did not want public. A system prompt rule keeps the agent from describing my role inaccurately.

## 9. UI

I rebuilt the interface as a full-page chat like ChatGPT and Claude. It has example prompt cards that copy into the input box for editing, a multi-line input (Shift+Enter for a new line, Enter to send), and follow-up suggestion chips after each answer. The chips come from a tested list in code, so every suggestion is a question the agent is known to handle, and no extra model call is needed. A "waking up the server" note appears after 6 seconds, because the free host sleeps when idle.

Several UI changes looked broken at first because my browser had cached old CSS and JS files. A hard refresh or private window fixed it.

## 10. Connectors (switchable data sources)

I added a Connectors panel, like data sources in an enterprise AI assistant. A registry in `connectors.py` lists each connector, and my choices are remembered in the browser. The server gives the model only the tools for connectors that are switched on. If a question needs one that is off, the agent tells the visitor which switch to flip.

- **Portfolio profile** and **Sample database:** the existing SQLite tools.
- **GitHub (live):** my public repositories and latest commits from GitHub's free API. It has a 10-minute cache, serves stale data if GitHub fails, skips forks, only accepts names of my own repositories, and uses only the first line of each commit message.
- **Google Search grounding:** I wrote and tested it, but live requests failed. The newer models returned `429 RESOURCE_EXHAUSTED` on my free key, and the 2.5 models returned `404`. It worked in the AI Studio playground but not through the API, so playground results do not predict API quota. A worse problem showed up too: when the tool failed, the model answered from memory as if it had searched. I fixed that with a system-prompt rule to say plainly when a tool is unavailable. The connector stays in the project, switched off by default, with an honest description.
- **Google Cloud docs:** a retrieval connector over four official documentation pages (BigQuery overview, BigQuery analytics overview, Dataflow overview, Pub/Sub overview). I looked up the official URLs first and found that Google's docs now live on `docs.cloud.google.com`. The tool fetches the pages from a fixed allowlist (visitors never supply a URL), strips page navigation, splits the text into passages of about 900 characters, and ranks them with BM25-style keyword scoring (`k1=1.5`, `b=0.75`). It rejects redirects outside Google's domains, fetches pages in parallel, caches them for 6 hours, backs off for 60 seconds after a failed fetch, and returns passages with page titles and links. I chose keyword ranking because the corpus is small and fixed, it costs no extra API quota, and tests are deterministic.

In testing, answers came from the right pages. One troubleshooting question got extra points that the pages did not support, so I tightened the prompt: partial matches must say what the documentation covers and stop there. I also learned that the keyword score does not measure relevance (a loosely related question scored as high as a clean match), so I use it only as a debugging aid.

## 11. Current state

- Live on Render with a pinned Python version, confirmed at `/health`.
- Function calling over four switchable connectors, with sources shown under each answer.
- Model-written SQL with two independent safety layers, plus a real FastMCP server exposing the same tools.
- Markdown instruction files as simple agent skills, and a harness that measures latency, intercepts errors and treats an empty reply as a failure.
- Rate limiting, input limits and escaped output.
- Automated tests and CI on every push, with a live evaluation of tool choice that runs when an API key is set.

## 12. What I learned

- **Whole-file rewrites are risky.** Pasting complete files into a terminal reverted earlier fixes without warning. Editing with diffs, plus tests and CI, makes regressions loud.
- **AI output needs checking.** The first AI made confident claims that were wrong or unsupported. A test, a diff, a live request or my own knowledge caught each one.
- **Mocked tests can pass while a live integration fails.** My Google Search tests were green while the real call returned errors. I now verify each live integration separately.
- **Read the generated SQL.** The grocery bug was invisible until I looked at the query the model actually wrote.
- **Design for the failing tool.** The agent should say so when a tool fails instead of answering from memory.
- **Protect secrets from the start.** Keys belong in the host's masked environment settings, never in a chat.

## 13. Known limits and next steps

- Docs retrieval is keyword-based over four pages. It can miss synonyms, and its content can be up to 6 hours old.
- Rate limits are in memory, so they reset when the server restarts.
- The web app calls the tools in-process. It is not itself an MCP client.
- Skills are always loaded into the prompt, not loaded on demand.
- I have not used Google's Agent Development Kit. This project uses the `google-genai` SDK directly.
- Possible next steps: a small load test, on-demand skills, and a true MCP client path.
